# Realtek RTL8169 / 8168 / 8111 / 810x Ethernet (r8169)

Most desktop and laptop mainboards from 2008 onwards have one of these
onboard: the RTL8111/8168 gigabit chip (PCI `10ec:8168`) or its 10/100
sibling RTL810x (`10ec:8136`). The driver is `drivers/r8169.c`. The
hardware-independent part, which covers registers, the chip table,
stop/reset/start sequences, MDIO and descriptor rings, is in
`drivers/r8169_hw.h`.

**QEMU does not emulate any of these chips.** The driver was written from
documentation and checked against a simulated chip
(`tools/test_r8169.py`). It has not run on real hardware yet. If you have
a PC with one of these chips, the steps below show what to look for, and a
report helps either way.

## Supported chips

The PCI IDs it binds to are `10ec:8169`, `10ec:8167`, `10ec:8168`,
`10ec:8161`, `10ec:8136`, `10ec:2502` and `10ec:2600` (Killer
E2500/E2600). It also binds to these OEM boards: `1186:4300` and
`1186:4302` (D-Link DGE-528T/530T), `1259:c107` (Corega), `1737:1032`
(Linksys EG1032, revision 3 only: subsystem `0x0024`), `16ec:0116` (USR 997902) and `10ff:8168` (TP-Link
TG-3468 v2). `10ec:8139` is left to `drivers/rtl8139.c`.

The ID only says the device belongs to the family. The revision comes
from the XID bits of TxConfig (register 0x40, mask `0x7cc00000`). A
revision missing from this table is **not** driven. The boot log then
prints `unknown chip revision, not used` along with the TxConfig value.

| XID | Chip | Bus | Notes (quirks applied) |
|---|---|---|---|
| `000` `008` `040` | RTL8169, 8169S, 8110S | PCI | writes 0x82 = 1 after reset; 8169S also sets PHY reg 0x0b = 0 |
| `100` `180` `7cc` `980` | 8169SB/8110SB, 8169SC/8110SC, 8169SBL, 8110SCe | PCI | as above, plus PHY wake; the SC parts get the 0x7C PCI timing value |
| `308` `340` | RTL8100E, 8101E | PCIe | 10/100 |
| `348` `248` `24c` `34c` | RTL8102E, 8102EL, 8103E | PCIe | 10/100, STOPREQ stop; the 8103E is woken from deep sleep through GPIO |
| `240` `408` `40c` `448` `440` | RTL8401E, 8105E, 8106E, 8402 | PCIe | 10/100, PHY powered on through PMCH |
| `300` `380` `384` | RTL8168B/8111B | PCIe | MACSTAT C+ mode; the first spin is reset after an RX FIFO overflow |
| `3c0` `3c4` `3c8` | RTL8168C/8111C, 8168CP | PCIe | STOPREQ stop; spin 2 is woken from deep sleep |
| `280` `288` | RTL8168D/8111D, 8168DP | PCIe | D: PHY powered on through PMCH. DP: waits for TxPoll to drain |
| **`2c0`** | **RTL8168E/8111E** | PCIe | PHY powered on through PMCH; STOPREQ stop |
| **`2c8`** | **RTL8168E-VL/8111E-VL** | PCIe | STOPREQ, then waits for the TX queue to empty; RxConfig early-off |
| **`480`** `488` | **RTL8168F/8111F**, 8411 | PCIe | as E-VL. The 8168F's multicast filter is broken, which doesn't matter here because all multicast is accepted |
| **`4c0`** `500` `508` | **RTL8168G/8111G**, 8168EP, 8168GU | PCIe | 8168G+ sequence (see below) |
| **`540`** `548` `5c8` | **RTL8168H/8111H**, 8168FP/8117, 8411B | PCIe | 8168G+ sequence. On a `10ec:8136` card this silicon is the 10/100 8106EUS/8107E |

The XID column lists the top 12 bits of TxConfig. Bits 22–20, the MAC
revision, are ignored, so `0x54100000` and `0x54000000` are both 8168H.

The 8168G-and-later sequence:

- **Stop:** gate RXDV (MISC 0xF0 bit 19), wait for TxConfig "queue
  empty", clear TE/RE, then wait until the MCU (0xD3) reports both FIFOs
  empty. STOPREQ is not used on these chips.
- **Start:** open the RXDV gate, write TxConfig and RxConfig, and only
  then set TE/RE. The older chips need TE/RE set *before* the config
  writes. A gate left closed means no frame is ever received, so this is
  the main reason a generic RTL8169 driver fails on 8168G/H boards.

All PCIe chips also get ASPM L0s/L1 and clock PM turned off in the PCIe
Link Control register, as FreeBSD's re(4) does by default. ASPM is
implicated in TX stalls on many 8168 revisions.

The driver does not apply Linux's per-revision PCIe-PHY ("ephy") tables,
PHY firmware patches, EEE, jumbo frames, checksum offload or MSI.
FreeBSD's re(4) leaves out the same things and works on these chips. The
interrupt is the legacy INTx line, shared, so the Config2 MSI enable bit
is cleared.

## Design

- **Rings:** 64 RX and 64 TX descriptors of 16 bytes each, 256-byte
  aligned, with EOR on the last one. Rings and buffers are in `.bss`, so
  their physical address is virtual minus `KERNEL_VMA`. That puts them
  inside the low 16 MiB, below 4 GiB with or without PAE, and every
  `addr_hi` is 0. RX buffers are 2 KiB, and RMS (0xDA) is set to 2048, so
  a frame never spans descriptors. A piece of a split frame is dropped
  anyway, along with frames that have the error-summary bit set or an
  impossible length. The 4-byte CRC is stripped.
- **Ownership:** a descriptor belongs to the chip while OWN is set. TX
  writes the address and length first and OWN last, then kicks the chip
  with TxPoll NPQ. All 64 TX slots are usable because, unlike the e1000,
  there is no head==tail ambiguity. Frames shorter than 60 bytes are
  zero-padded. An RX slot is re-armed with OWN | size (| EOR) and
  opts2 = 0.
- **Interrupts:** ROK, RER, TER, RDU, LinkChg, FIFO overflow and SERR.
  The handler reads ISR. A value of 0 means the interrupt belongs to
  another device on the shared line, and 0xFFFF means the device is gone;
  both are ignored. Otherwise it acknowledges the bits by writing them
  back and wakes I/O sleepers. As with the e1000, frames are handled in
  process context by `net_poll_all()` because lwIP is not reentrant.
- **Recovery:** if posted frames make no progress for 2 s, or on a PCI
  system error, the driver does a full stop/reset/start with fresh rings.
  The 8168B spin 1 also gets one after an RX FIFO overflow. Each recovery
  is logged to klog.
- **Registers:** MMIO when there is a memory BAR below 4 GiB (BAR1 on
  the 8169, BAR2 on PCIe chips). Otherwise it uses the I/O BAR, which
  every chip has.
- **MAC address:** read from IDR0–5, which the chip loads from its
  EEPROM/eFuse at power-on. If that is blank, the driver uses a locally
  administered `02:10:ec:<bus>:<dev/fn>:<xid>` instead and says
  `(generated)` in the boot log.
- **PHY:** the driver resets the PHY through MDIO (PHYAR 0x60, BMCR
  bit 15). It then advertises 10/100 half and full duplex with pause, adds
  1000 full and half duplex on gigabit chips, and restarts
  autonegotiation. Link, speed and duplex are read from PHYstatus (0x6C).
- **Absent hardware:** with none of the IDs above present, the boot log
  prints `[R8169] not present` and no register is touched. The e1000 and
  RTL8139 paths are unchanged. The first NIC found becomes `eth0`
  (lwIP's interface), and later ones become `eth1` and up.

## Testing on a real PC

1. Build the image (`make limine-iso`) and write it to a USB stick, or
   install it (`docs/install.md`). Plug a cable into the Realtek port
   with a DHCP server on the network.
2. Boot and read the kernel log, either with `dmesg` or on serial. You
   should see one line like:

   ```
   [R8169] 10ec:8168 RTL8168H/8111H (TxConfig 0x54100000) mmio=0xf7d04000 irq=11 mac=xx:xx:xx:xx:xx:xx phy=ok aspm=off link=down
   ```

   `link=down` is normal at this point because autonegotiation was just
   restarted and takes 2–3 s. These are problems:
   - `unknown chip revision, not used`: report the TxConfig value. The
     revision needs a table entry, and maybe a quirk.
   - `phy=no-answer`: MDIO through PHYAR failed. On an 8168G or later this
     would mean the PHY has to be reached through OCP (0xB8), which this
     driver doesn't do yet.
   - `reset-timeout`: the chip did not finish its reset.
   - `(generated)` after the MAC: IDR was blank. The NIC still works,
     with a made-up address.
   - `has no usable BAR`: the firmware assigned no resources to the NIC.
3. Then `[LWIP] eth0 DHCP started` should appear, followed by an address.
   Check with:

   ```sh
   cat /proc/netif
   # eth0: r8169 up chip=RTL8168H/8111H mmio=0x... irq=11 mac=... link=up/1000/fd rxnext=.. txpend=0 rxerr=0 rdu=0 missed=0 resets=0 txpkts=.. rxpkts=.. drop=0 ip=...
   ping -c 3 <gateway>
   wget http://example.com/ -O /tmp/x    # or: apk update in the Alpine chroot
   ```

   These are the fields to look at:
   - `link=` should read `up/<speed>/<duplex>`.
   - `rxpkts` should rise steadily while broadcast traffic is on the
     network.
   - `txpend` should be 0 when idle.
   - `resets` should stay 0. If it grows, the TX watchdog fired, and klog
     has an `[R8169] transmit stalled` line.
   - `rdu` counts RX-ring-full events (bursts the poller fell behind on).
   - `missed` is the chip's missed-packet counter.
   - `rxerr` counts CRC errors and split frames. A large value points to
     cabling or a duplex mismatch.
4. If nothing is received at all on an 8168G/H (`rxpkts` stays 0 while
   `link=up`), suspect the RXDV gate (MISC bit 19). Please report it,
   together with the chip line from the boot log.

## Host test

`python3 tools/test_r8169.py` is also run by `smoke-toybox` and so by
`make check`. It builds `tools/test_r8169.c` with ASan/UBSan, against a
simulated register file and DMA engine. The tests cover:

- the TxConfig chip table (every entry reachable; 8139, 8125 and
  all-ones rejected)
- the start order for pre-G chips versus 8168G+ (TE/RE against the config
  writes, the RXDV gate), the stop sequence, Config2 MSI, the 8169 0x82
  and 8110SC 0x7C quirks, and the E-VL/G early-off bits
- PHY bring-up through the PHYAR handshake, including 10/100 chips and a
  PHY that never answers (bounded time)
- TX: a full ring of 64, in-order reclaim that stops at an owned slot,
  stall watchdog timing and tick wrap, and ten rings of wraparound with
  EOR checked and padding
- RX: twenty rings of wraparound, a ring left full until RDU and then
  resumed, budgeted polls, CRC errors and three-piece frames dropped,
  impossible lengths, and a clean re-arm after reset

Mutations such as dropping EOR, ignoring OWN on reclaim, TE/RE too early
on G+, no CRC strip or a reserved TX slot each fail the test.
